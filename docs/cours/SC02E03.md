## Les différents types de test

On a 3 types de tests :

- Les tests unitaires
    - Permet de tester une fonction isolée
- Les tests d'intégration
    - Permettent de tester une partie du système
    - ex : tester l'authentification, tester la réception de formulaires, tester une méthode de paiement, tester l'affichage d'un modèle 3D...
    - Les tests d'intégration, contrairement aux tests unitaires, concernent un ensemble de fonctions
- Les test E2E
    - Tests End to end, qui concernent plus qu'une partie de l'écosystème, ici on commence le test depuis l'expérience utilisateur, jusqu'à l'aboutissement de ce système.
    - ex: tests d'authentification, sauf que cette fois, on va regarder plus que les fonctions appelées lorsqu'on se connecte, on vérifie aussi que tout se passe bien coté client
    - ex: tests concernant une page entière


## Structure AAA

Lorsqu'on fait un test on suit toujours cette structure :

- Arrange : On met en place les données pour le test
- Act : On exécute notre test
- Assert : On vérifie les résultats de notre test

## Les tests unitaires

Pour les tests de notre API et notre client, on va utiliser 2 outils différents : 
- Coté API : node:tests & node:assert
- Coté client : vitest

### Côté API

Pour notre premier test, on va utiliser une fonction fictive qui est la suivante : 

On la rajoute dans /lib/validator.ts , qui sont un dossier et un fichier qu'on va créer pour l'occasion

```
export function isValidPassword(password: string) {

  // Mot passe valide :
  // - au moins 8 caractères (CNIL recommande 12)
  // - au moins un chiffre
  // - au moins une majuscule
  // - au moins une minuscule
  // - au moins un caractère spécial

  
  if (password.length < 8) { return false; }

  if (!/[0-9]/.test(password)) { return false; }

  if (!/[A-Z]/.test(password)) { return false; }

  if (!/[a-z]/.test(password)) { return false; }

  if (!/[!@#$%^&*(),.?":{}|<>;'`~]/.test(password)) { return false; }

  return true;

}
```

On va créer un fichier `validators.test.ts` dans le même dossier, afin de tester cette fonction

Une fois qu'on a écrit nos tests, on va rajouter un script dans package.json, pour lancer nos tests

### Côté Client

Pour faire les tests côté client, on va utiliser vitest, qu'on va installer dans le dossier client :
`npm install -D vitest` 

On va aussi ajouter 2 scripts de test dans le package.json du client

```
"scripts":{
    ...

    "test": "vitest run",
    "test:watch": "vitest"
}
```

## Tests d'intégration

Lorsqu'on veut tester plus en profondeur notre API, on va devoir consulter notre BDD
Problème : on ne veut pas rajouter ou supprimer des informations sur notre BDD destinée à la prod
Solution : on va créer un environnement de test, générant une BDD avant chaque test

- Dans le dossier api, créer un dossier test, qui contiendra lui même un dossier config
    - on peut lancer la commande depuis la racine de nos 2 projets`mkdir -p api/test/config` ou créer les fichiers dans l'ide, ou faire 2 mkdir à la suite

- Dans le dossier config on va créer un fichier `global-setup.ts` qui va nous permettre avant les test de créer une BDD temporaire, qu'on va vider avant chaque test, afin de pouvoir avoir un environnement propre à nos tests

- Ensuite on va créer un fichier index.ts, qui va nous permettre de centraliser les requêtes et de ne pas avoir à reécrire tout le process de requête à chaque test, ce fichier index.ts va utiliser axios, qui est un package permettant de faire des requêtes http, on va donc installer le package dans notre api (on se déplace dans /api puis :)`npm install axios`

### Erreur de droits lorsqu'on lance `npm run db:migrate:dev`

Il est possible que l'utilisateur oquiz n'ait pas le droit de créer une BDD, on doit lui rajouter ces droits en se connecter à psql : `sudo -u postgres psql` puis en tapant la commande `ALTER USER oquiz CREATEDB`
