# Centraliser la gestion d'erreur

On va créer un global error handler, qui va s'occuper de gérer les erreurs globales
On va aussi créer des classes d'erreurs personalisées, afin d'envoyer des erreurs plus détaillées aux clients - ces classes d'erreurs personalisées nous permettront à termes de préparer des comportements spécifiques à chaques erreurs

Donc : 
- Le code sera plus clean
- Les erreurs seront mieux catchées
- Les clients seront mieux informés

Avec `global-error-handler` on centralise la gestion d'erreur via un middleware, on veut afiner les gestions d'erreurs à travers des classes, et on va en profiter pour regarder le typage de nos erreurs avec zod
- On installe le package zod dans le dossier `api` via `npm i zod`


- Globalement : 

- On a créé un fichier utils contenant 2 fonctions permettant de vérifier que les informations qu'on reçoit du client sont du bon type et du bon format (un id correct (`parseIntFromParams`) et un body (`parseBodyFromParams`)avec un name à l'intérieur). Ces 2 fonctions utilisent zod, qui fonctionne comme joi, mais va aussi nous permettre de throw des erreurs, qu'on va intercepter
- On a créé des classes d'erreurs nous permettant d'affiner notre réaction à chaque erreurs, sur un projet qu'on développerait, ça nous permettrait d'avoir des réactions != en fonction du type d'erreurs
- Ces classes d'erreurs utilisées à travers un throw ConflitError ou NotFoundError, vont être récupérées par le middleware qu'on a créé 
- A la fin de nos routes, on a un middleware qui centralise la réception des erreurs, où on va pouvoir regarder si l'erreur est de type Conflict, HttpClientError, NotFound, ou 500 


- Le comportement résumé de notre code :

- App.js met en place des routes
- Ces routes appellent des controllers
- Dans nos controllers on vérifie si l'information est bonne ou pas, on regarde aussi si on a une erreur
    - Si on a une erreur, on envoie l'erreur au middleware qui centralise les erreurs
    - Si on a pas d'erreur, on répond positivement à la requête

# ESLint

ESLint est un linter, il analyse le code pour détecter des erreurs de syntaxe et des mauvaises pratiques, on doit l'installer puis l'exécuter
- installation `npm install --save-dev eslint @eslint/js typescript typescript-eslint` - à lancer dans le dossier api
- ensuite on configure eslint en rajoutant un fichier à la racine qu'on va appeler `eslint.config.js`
- On rajoute dans package.json les scripts liés à lint, (cf : `lint` et `lint:fix` dans le package.json)

Une fois qu'eslint est configuré, on peut lancer le linter via `npm run lint`, ensuite si on veut fixer la plupart des erreurs automatiquement, on va lancer `npm run lint:fix`

- Si des erreurs persistent, on peut aller les fixer en faisant un ctrl + click sur le chemin mentionné dans l'erreur, puis on édite le code nous même
- Si certaines lignes nous conviennent telles qu'elles sont malgré l'avertissement de eslint, on peut demander à eslint d'ignorer cette ligne avec le commentaire sur la même ligne : `// eslint-disable-line`

# Husky

Husky va nous permettre de réaliser des actions avant de faire un commit, si ces actions ne sont pas positives, le commit ne passera pas : dans notre cas, on va lancer le linter avant de faire commit via husky, pour que le code push soit propre
- Pour installer husky : `npm install --save-dev husky` dans notre dossier api
- Ensuite on crée un dossier de config pour husky, dans lequel on va spécifier la configuration qu'on souhaite
- Dans le dossier `.husky`, on va rajouter un fichier `pre-commit` dans lequel on va lancer eslint
- Si le linter trouve des problèmes, le commit ne sera pas réalisé
- On configure git pour que husky soit lancé lorsque un commit est exécuté
    - dans le dossier .husky -> on rajoute les droits d'exécution au fichier pre-commit `chmod +x pre-commit`
    - on configure git à la racine de notre projet (au dessus de `client` et `api`) en faisant un git config core.hooksPath api/.husky -> de cette manière, quand git va réaliser un commit, il va commencer par lancer husky
- Maintenant on peut tester de faire un commit, et voir que husky lance bien eslint

# Github Actions

On va créer un dossier `workflows` dans le dossier .github, ce fichier permettra de réaliser des actions lorsqu'un push est effectué

Dans workflows on va rajouter un fichier au nom de notre choix, dans lequel on va spécifier:
- le contexte dans lequel les actions doivent être réalisées (ex : après un commit sur main ou master)
- l'environnemnt dans lequel le réaliser (ex: ubuntu latest)
- les actions à réaliser (installer les packages, setup prisma, et lancer les tests)

- On peut aussi rajouter le fichier directement dans notre projet github via l'onglet `actions`, dans lequel on va pouvoir écrire toutes les taches à réaliser
